# 30분 전체 지도

이 문서 하나만 읽어도 회의에서 말은 통합니다.

## 1. 전체 구조를 한 장으로

사용자가 질문을 던지고 답을 받기까지, 로컬 LLM 시스템은 이렇게 생겼습니다.

```
[사용자]
   |  "육아휴직 조건이 뭐야?"
   v
[웹 UI / 챗봇 화면]
   |
   v
[애플리케이션 서버]  <- 여기를 당신이 만듭니다
   |     |
   |     +--> [벡터 DB]  사내 문서에서 관련 문단 찾아오기 (RAG)
   |     +--> [사내 API]  실제 시스템 조회하기 (에이전트 / MCP)
   v
[LLM 추론 서버]  <- 모델이 실제로 도는 곳 (GPU)
   |
   v
[모델 파일]  예: Qwen3-32B, Llama, Gemma ...
```

핵심은 **LLM 자체는 그냥 "글을 이어 쓰는 엔진"일 뿐**이라는 겁니다. 사내 지식도, 시스템 접근 권한도 없습니다. 그걸 붙여주는 게 RAG와 에이전트고, 그게 당신의 일입니다.

## 2. LLM은 뭘 하는 물건인가

**LLM은 "다음에 올 단어를 확률로 찍는 기계"입니다.** 그게 전부입니다.

"오늘 점심은 김치" 까지 주면 → "찌개"(42%), "볶음밥"(31%), "전"(9%)... 이런 식으로 확률을 계산하고 하나를 골라 붙입니다. 그리고 그 결과를 다시 입력에 넣고 또 다음 단어를 찍습니다. 이걸 반복해서 문장이 나옵니다.

"그게 어떻게 추론이 되냐" 싶겠지만, 인터넷 규모의 글을 다 읽고 다음 단어를 맞추는 훈련을 하다 보면 문법, 상식, 코드 패턴, 추론 흐름까지 그 확률 안에 녹아들어 갑니다. 그게 현재 LLM의 정체입니다.

여기서 두 가지가 바로 따라 나옵니다.

1. **모델은 "모른다"는 개념이 약합니다.** 확률상 그럴듯한 단어를 계속 붙이다 보니, 없는 규정 조항도 그럴듯하게 지어냅니다. 이걸 **환각(hallucination)** 이라 합니다.
2. **모델은 학습 시점 이후를 모릅니다.** 우리 회사 내부 문서는 당연히 학습된 적이 없습니다.

이 둘을 해결하는 게 RAG입니다.

## 3. RAG: 오픈북 시험으로 바꾸기

**RAG(검색 증강 생성)** 는 이름은 거창하지만 아이디어는 단순합니다.

모델에게 암기 시험을 보게 하지 말고, **답이 적힌 페이지를 찾아서 손에 쥐여준 뒤 문제를 풀게** 하는 겁니다.

```
질문: "육아휴직 조건이 뭐야?"
   |
   v
1) 사내 문서 중에서 질문과 가장 관련 있는 문단 5개를 찾는다
   |
   v
2) 모델에게 이렇게 물어본다:
   "아래 자료를 근거로만 답해. 자료에 없으면 모른다고 해.
    [자료] 취업규칙 제32조 ... (찾아온 문단들)
    [질문] 육아휴직 조건이 뭐야?"
   |
   v
3) 모델이 자료를 읽고 답 + 출처를 낸다
```

이게 사내 LLM 프로젝트의 90%입니다. 모델을 다시 학습시키지 않고도 사내 지식을 쓰게 만드는 가장 싸고 빠르고 안전한 방법이라서요. 문서가 바뀌면 벡터 DB만 갱신하면 끝입니다.

관련 문단을 "찾는" 방법이 [[21-토큰과 임베딩|임베딩]]이고, 저장소가 [[10-용어사전#벡터 DB|벡터 DB]]입니다.

## 4. 에이전트: 모델에게 손발 달아주기

RAG는 모델이 **읽기**만 합니다. 에이전트는 모델이 **행동**하게 합니다.

원리는 의외로 시시합니다. 모델에게 이렇게 말해두는 겁니다.

> "너는 이런 도구들을 쓸 수 있어: `조회_고객정보(고객번호)`, `조회_환율(통화)`.
> 도구가 필요하면 답 대신 도구 이름과 인자를 JSON으로 뱉어."

모델이 `{"tool":"조회_환율","args":{"통화":"USD"}}` 를 뱉으면, **당신의 코드가** 실제 API를 호출하고, 결과를 다시 모델에게 주고, 모델이 최종 문장을 만듭니다.

즉 **실제로 API를 호출하는 건 모델이 아니라 당신 코드**입니다. 모델은 "이걸 부르면 될 것 같은데?"라고 제안만 합니다. 이 사실이 보안 심의에서 아주 중요합니다. 권한 통제는 전부 당신 코드에서 합니다.

## 5. MCP: 도구를 꽂는 표준 규격

도구를 하나씩 직접 짜다 보면 금방 지저분해집니다. 같은 사내 API를 챗봇에서도, IDE에서도, 다른 팀 시스템에서도 쓰려면 매번 다시 짜야 하니까요.

**MCP(Model Context Protocol)** 는 그걸 위한 **USB 규격** 같은 겁니다. 도구를 MCP 서버로 한 번 만들어 두면, MCP를 지원하는 어떤 앱이든 거기에 꽂아 쓸 수 있습니다.

```
[MCP 서버: 사내 인사 시스템]  ─┐
[MCP 서버: 사내 문서 검색]    ─┼─> [MCP 클라이언트 = 우리 챗봇 / IDE / 다른 앱]
[MCP 서버: 사내 코드 저장소]  ─┘
```

폐쇄망에서도 문제없습니다. MCP는 로컬 프로세스 간 통신(stdio)이나 사내 HTTP로 돕니다. 외부 인터넷이 필요 없습니다.

## 6. 그래서 뭘 결정해야 하나

구축할 때 실제로 결정해야 하는 항목은 이 정도입니다.

1. **어떤 모델을 쓸 것인가** → 라이선스, 한국어 성능, 크기 ([[23-모델 크기와 양자화]])
2. **무엇으로 서빙할 것인가** → Ollama / vLLM / llama.cpp ([[41-서빙 스택 선택]])
3. **GPU를 얼마나 살 것인가** → 모델 크기 × 동시 사용자 ([[42-GPU 사이징]])
4. **사내 지식을 어떻게 넣을 것인가** → 거의 항상 RAG ([[25-파인튜닝 vs RAG vs 프롬프트]])
5. **어디까지 자동화할 것인가** → 읽기 전용부터 시작 ([[43-금융권 보안 규제 고려사항]])

## 정리

정리하면, LLM은 다음 단어를 찍는 엔진이고, RAG는 그 엔진에 사내 자료를 쥐여주는 것이고, 에이전트는 손발을 달아주는 것이고, MCP는 그 손발을 꽂는 표준 규격입니다. 당신이 만들 것은 이 넷을 이어붙이는 애플리케이션 서버입니다.
