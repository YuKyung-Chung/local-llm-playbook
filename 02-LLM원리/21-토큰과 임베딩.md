# 토큰과 임베딩

RAG를 만들려면 이 둘은 확실히 잡고 가야 합니다.

## 1. 토큰

### 왜 단어가 아니라 토큰인가

세상의 모든 단어를 사전에 담으면 사전이 무한히 커집니다. 오타, 신조어, 사람 이름은 감당이 안 됩니다.
그래서 **자주 나오는 조각 단위로 쪼갭니다.** 이걸 서브워드 토큰화라고 합니다.

```
"unbelievable"  ->  ["un", "believ", "able"]
"육아휴직"       ->  ["육아", "휴", "직"]  (모델마다 다름)
```

이러면 사전 크기는 5만~15만 개로 고정되고, 처음 보는 단어도 조각을 조합해 표현할 수 있습니다.

### 한국어는 토큰을 많이 먹습니다

이게 실무에서 진짜 문제가 됩니다.

| 문장 | 대략 토큰 수 |
|---|---|
| `Hello, how are you?` (19자) | 6개 |
| `안녕하세요, 어떻게 지내세요?` (15자) | 12~18개 |

같은 뜻인데 **한국어가 2~3배**를 씁니다. 대부분의 모델이 영어 위주로 토크나이저를 만들었기 때문입니다.

**따라오는 결과:**
- 컨텍스트 윈도우가 실질적으로 1/2~1/3로 줄어듭니다. 32K라고 해도 한국어로는 훨씬 짧습니다.
- 생성 속도가 느려집니다. 같은 분량을 만드는 데 토큰을 더 뱉어야 하니까요.
- **모델 선택 기준이 됩니다.** 한국어 토큰 효율이 좋은 모델(한국어 데이터를 많이 본 모델)이 실제 운영에서 유리합니다.

### 실무 감각

- 한국어 1,000자 문서 ≈ 700~1,200 토큰
- A4 한 장 ≈ 1,500~2,000 토큰
- 32K 컨텍스트 ≈ 한국어 A4 15~20장 정도

RAG에서 "문서 5개를 붙여 넣는다"고 할 때 이 계산을 해야 컨텍스트를 넘기지 않습니다.

## 2. 임베딩

### 뜻을 좌표로 바꾸기

임베딩은 **문장을 숫자 벡터로 바꿔서, 뜻이 비슷하면 벡터도 가깝게** 만드는 기술입니다.

색깔로 비유해봅시다. 빨강은 (255, 0, 0), 주황은 (255, 165, 0), 파랑은 (0, 0, 255) 입니다.
숫자만 봐도 빨강과 주황이 가깝고 파랑은 멀다는 걸 알 수 있죠.

문장도 똑같이 합니다. 다만 3개가 아니라 1024개 정도의 숫자를 씁니다.

```
"육아휴직 신청 방법"   -> [0.21, -0.55, 0.13, ... ]  (1024개)
"출산휴가 어떻게 내나요" -> [0.19, -0.51, 0.15, ... ]  <- 가까움
"이번 달 환율 전망"     -> [-0.72, 0.31, -0.44, ...]  <- 멂
```

### 왜 이게 검색에 혁명인가

기존 키워드 검색은 글자가 같아야 찾습니다. "육아휴직"으로 검색하면 "출산휴가"가 적힌 문서는 못 찾습니다.
임베딩 검색은 **글자가 달라도 뜻이 통하면** 찾습니다. 이게 RAG의 핵심입니다.

### 다만 키워드 검색도 버리면 안 됩니다

반대 상황도 있습니다.
- "제32조" 를 찾을 때 → 임베딩은 숫자 조항 구분을 잘 못 합니다. 키워드 검색이 압승.
- "KB-2024-017 규정" 같은 사내 코드 → 마찬가지.

그래서 실무에서는 **둘을 섞습니다.** 이게 [[10-용어사전#하이브리드 검색|하이브리드 검색]]입니다. 금융권 문서는 조항 번호와 상품 코드가 많아서 특히 중요합니다.

### 임베딩 모델은 LLM과 별개입니다

자주 헷갈리는 부분입니다.

| | 하는 일 | 예시 |
|---|---|---|
| **생성 모델 (LLM)** | 답변 문장을 만든다 | Qwen3-32B-Instruct |
| **임베딩 모델** | 문장을 벡터로 바꾼다 | bge-m3, multilingual-e5 |

**둘 다 따로 반입해야 합니다.** 폐쇄망 반입 목록에서 임베딩 모델을 빼먹는 사고가 흔합니다.

임베딩 모델 고를 때 볼 것:
1. **한국어 지원 여부** (다국어 모델이거나 한국어 학습된 것)
2. 차원 수 (1024 정도면 충분)
3. 최대 입력 길이 (512 토큰짜리가 많음. 청크 크기를 여기 맞춰야 함)
4. 라이선스

실습에서는 `bge-m3` 계열을 씁니다. 한국어가 되고, 다국어이고, 라이선스가 무난합니다.

### 절대 규칙 하나

**저장할 때와 검색할 때 반드시 같은 임베딩 모델을 써야 합니다.**
모델을 바꾸면 벡터 DB를 **전부 다시 만들어야** 합니다. 문서 10만 건이면 몇 시간이 걸립니다. 그래서 임베딩 모델 선택은 초기에 신중하게 하고, 어떤 모델을 썼는지 반드시 기록해두세요.

## 정리

정리하면, 토큰은 모델이 글을 세는 단위이고 한국어는 비싸게 먹히며, 임베딩은 뜻을 좌표로 바꿔 의미 검색을 가능하게 하는 별도의 모델입니다. 이 둘의 실무 함정은 "한국어 컨텍스트 부족"과 "임베딩 모델 바꾸면 재색인"입니다.
