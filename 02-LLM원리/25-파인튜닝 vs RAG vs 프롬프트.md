# 파인튜닝 vs RAG vs 프롬프트

**"사내 데이터를 어떻게 모델에 넣나요?"** 이 질문에 대한 답입니다. 프로젝트 방향을 결정하는 가장 중요한 문서입니다.

## 세 가지 선택지

신입사원을 교육시킨다고 비유해봅시다.

| 방법 | 비유 | 실제 |
|---|---|---|
| **프롬프트** | 일 시킬 때마다 지시사항을 설명 | 시스템 프롬프트에 규칙을 적음 |
| **RAG** | 필요할 때 찾아볼 사내 자료실을 알려줌 | 질문마다 관련 문서를 검색해 같이 넣어줌 |
| **파인튜닝** | 신입 연수를 몇 달 시켜서 회사 방식을 몸에 배게 함 | 모델 가중치를 우리 데이터로 추가 학습 |

## 비교표

| | 프롬프트 | RAG | 파인튜닝 |
|---|---|---|---|
| 비용 | 거의 없음 | 낮음 | 높음 (GPU + 사람 시간) |
| 구축 기간 | 몇 시간 | 1~4주 | 1~3개월 |
| 최신 정보 반영 | 매번 수정 | **문서만 갱신하면 즉시** | 재학습 필요 |
| 출처 표시 | 불가 | **가능** | 불가 |
| 환각 억제 | 약함 | **강함** | 중간 |
| 말투/형식 학습 | 가능 | 제한적 | **매우 강함** |
| 보안 심의 | 쉬움 | 중간 | **어려움** (실데이터가 모델에 박힘) |
| 되돌리기 | 즉시 | 즉시 | 어려움 |

## 결론: 순서가 정해져 있습니다

```
1. 프롬프트로 해본다        <- 여기서 해결되면 끝
        |  부족하면
        v
2. RAG를 붙인다             <- 사내 지식 문제는 90% 여기서 해결
        |  그래도 부족하면
        v
3. 그때 파인튜닝을 검토한다  <- 대부분 여기까지 안 감
```

**"사내 문서로 파인튜닝해서 우리 회사 전용 GPT를 만들자"는 거의 항상 잘못된 출발점입니다.** 이유가 세 가지입니다.

1. **지식 주입에 비효율적입니다.** 파인튜닝은 "말투와 형식"을 가르치는 데는 강하지만, "사실 지식"을 넣는 데는 RAG보다 훨씬 나쁩니다. 학습시켜도 여전히 지어냅니다.
2. **문서가 바뀌면 답이 없습니다.** 취업규칙 개정될 때마다 재학습할 수는 없습니다.
3. **금융권에서 심의가 지옥입니다.** 개인정보나 신용정보가 모델 가중치에 박히면 삭제 요구(잊힐 권리) 대응이 사실상 불가능합니다. RAG는 벡터 DB에서 지우면 끝입니다.

## 파인튜닝이 정말 필요한 경우

이럴 때는 검토할 만합니다.

- **특정 출력 형식을 반드시 지켜야 할 때.** 사내 표준 보고서 양식, 특정 JSON 스키마
- **도메인 말투가 중요할 때.** 금융 상담 어투, 약관 문체
- **RAG로 넣기엔 너무 방대한 암묵지**를 압축해야 할 때
- **응답 속도가 중요해서** 긴 프롬프트를 줄여야 할 때 (프롬프트에 넣던 규칙을 모델에 심어 토큰 절약)

이때도 전체 파인튜닝이 아니라 **LoRA/QLoRA**를 씁니다. GPU 한두 장으로 되고, 원본 모델은 그대로 두고 얇은 어댑터만 학습합니다. 문제가 생기면 어댑터만 떼면 됩니다.

## RAG와 파인튜닝은 배타적이지 않습니다

성숙한 시스템은 둘 다 씁니다.
- 파인튜닝으로 **말투와 출력 형식**을 잡고
- RAG로 **사실 지식**을 공급합니다

다만 순서는 RAG가 먼저입니다.

## 우리 프로젝트에 적용하면

1차 목표인 "사내 문서 질의응답"은 **100% RAG 영역**입니다. 파인튜닝은 검토하지 마세요.
[[35-실습5 RAG 챗봇 만들기]] 로 바로 가면 됩니다.

## 정리

정리하면, 프롬프트 → RAG → 파인튜닝 순으로 시도하고, 사내 지식 문제는 대부분 RAG에서 끝나며, 금융권에서 파인튜닝은 성능이 아니라 **규제 리스크** 때문에 마지막 카드입니다.
